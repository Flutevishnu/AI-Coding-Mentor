# CLAUDE.md

Backend for **BaseCase**, a Socratic coding-interview tutor. A LangGraph state machine (Python 3.12, Google Gemini via `langchain-google-genai`) guides a student from plan → code → review without ever writing the solution for them. The frontend lives in the separate `basecase` repo.

## Commands

```bash
uv sync                                                   # install deps
uv run langgraph dev --config langgraph.dev.json          # local dev server + Studio (port 2024)
```

- Use `langgraph.dev.json` locally. `langgraph.json` is the production config and sets `http.disable_assistants: true`, which makes `/assistants/search` 404 and breaks Studio.
- Quick health checks: `GET http://127.0.0.1:2024/ok`, and `POST /assistants/search` with body `{"limit":10}` should list the `agent` graph.
- There are no tests or linters configured.

## Layout

- `agents/mentor.py`: everything that matters. State, Pydantic schemas, nodes, routing, and the compiled `mentor_graph` (exported as graph `agent`).
- `core/config.py`: `pydantic-settings` `Settings` loaded from `.env`, exposed as `settings`.
- `core/logging_config.py`: the `mentor` logger, writing to `<LOG_DIR>/<ENV>.log` (rotating) and the console. Import `logger` from here.
- `mentor_agent.ipynb`: an outdated prototype (OpenAI/Novita, Postgres checkpointer, different nodes). It doesn't reflect the current graph, so don't treat it as the source of truth.
- `Dockerfile`: generated by `langgraph dockerfile` on the `langchain/langgraph-api` base image.

## Graph architecture

`MentorState.current_phase` (`IDEATION` | `CODING` | `REVIEW`) drives routing. Each run handles one user turn, then ends.

```
START ─route_on_phase─┬─ IDEATION ─────────────→ ideation_node ─(ApprovePlan tool call?)→ transition_node → END
                      ├─ CODING, no submission → coding_node → END
                      └─ CODING + code_submission → review_node ─(correct?)→ extractor_node → END
```

- **ideation_node**: BIG_MODEL bound to the `ApprovePlan` tool. Personalised with `past_related_problems`, `technical_blindspots` and `behavioral_traits` from state.
- **transition_node**: answers the tool call with a `ToolMessage`, sets phase to `CODING`, and stores `agreed_plan`.
- **coding_node**: BIG_MODEL bound to `GenerateVisualization` (array / linked_list / binary_tree / hashmap / matrix step animations for the frontend). Malformed tool args are retried through `retry_validated_tool_call`.
- **review_node**: SMALL_MODEL with structured output `CodeReview`. Incorrect code returns to `CODING` with a hint. Correct code sets phase to `REVIEW`, stores `review`, and clears `code_submission`.
- **extractor_node**: SMALL_MODEL with structured output `SessionSummary`, built from the transcript. `concept_updates[].tag` must come from `problem_tags`. The result goes in `session_summary`. The Express backend persists it when LangGraph posts the run-completion webhook (`/api/webhooks/evaluations`).

Who supplies the inputs (the cross-service details are in `C:\dev\BaseCase-Docs\ARCHITECTURE.md`):
- **Orchestrator**, once, when the thread is created: `problem_tags`, `technical_blindspots`, `behavioral_traits`, `past_related_problems`.
- **Frontend**, in every chat run's `input`: `messages`, `problem_description`, `current_phase`.
- **Orchestrator**, in the submit run's `input`: `code_submission` and `submission_id`.

## Conventions

- **Prompts live in the LangSmith Prompt Hub** (`basecase-mentor-ideation|coding|review|extractor`) and are pulled at import time in `PROMPTS`. Change prompt wording in the Hub, not in code. Template variables passed through `format_prompt(...)` must match the Hub prompt's inputs.
- **Never let a node raise.** Wrap model calls in `safe_invoke` and prompt rendering in `format_prompt`. On failure, return `FALLBACK_MESSAGE` (or a friendly message) and log with `logger.exception`.
- **Structured outputs:** use `.with_structured_output(Schema, include_raw=True)` together with `retry_structured_output`. Tool calls use `bind_tools` together with `retry_validated_tool_call`. Both feed the validation error back as a `SystemMessage` and retry up to 3 times.
- **Schema `Field(description=...)` text is part of the prompt.** The model reads it, so edit it with the same care as prompt wording.
- **Model choice:** BIG_MODEL for conversation (ideation, coding), SMALL_MODEL for review and extraction. Both are set in `.env`; don't hard-code model names.
- Logging style: `logger.info("Message | key=%s", value)`.

## Configuration gotchas

- `Settings` requires `GOOGLE_API_KEY`, `LANGSMITH_API_KEY`, `LANGCHAIN_PROJECT`, `LANGCHAIN_TRACING_V2`, `BIG_MODEL`, `SMALL_MODEL`, `ENV`, `LOG_DIR` and `LOG_LEVEL`, with no defaults. `.env.sample` is missing `LANGCHAIN_PROJECT` and `LANGCHAIN_TRACING_V2`, and the README wrongly calls `ENV`, `LOG_DIR` and `LOG_LEVEL` optional.
- Importing `agents.mentor` makes network calls to LangSmith. With no connectivity or a bad key, the server won't start.
- `langgraph-api` is pinned at 0.8.7, which is End of Life.
- `langchain-openai` is a dependency used only by the old notebook.
